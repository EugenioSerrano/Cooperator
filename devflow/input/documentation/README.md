# Input — Documentation (raw external reference)

**Methodology version:** 5.2

## Purpose

This folder stores **documentation of external systems, libraries, APIs, and
vendors** that integrate with the project, along with manuals and
specifications of the legacy system.

This is not documentation generated by the team — it is third-party reference
material: API manuals, protocol specifications, datasheets, integration guides,
vendor PDFs, current system manuals, etc.

---

## What goes here?

- API manuals from vendors and external services.
- File format specifications (fixed-width, CSV, XML, JSON).
- Documentation of third-party libraries and frameworks used.
- Integration guides for external services.
- PDFs and datasheets from hardware vendors.
- Technical terms and conditions of contracted services.
- Functional/technical manuals of the legacy system.

## What does NOT go here?

- Analysis or interpretation of the material → `discovery/DISC-NNN` (material
  unknown) or `analysis/` (domain understanding).
- Integration decisions → `adrs/`.
- Team-generated documentation (specs, ADRs, reviews, etc.) — lives in its
  corresponding folders within `devflow/`.

---

## Organization

Subfolders by vendor or system:

```
documentation/
├── vendor-a/       → Vendor A documentation
├── vendor-b/       → Vendor B documentation
├── framework-x/    → Framework X documentation
└── legacy-system/  → Current system manuals
```

---

## Notes

- These files are **reference only**. They are not modified.
- Keep files in their original format (PDF, DOCX, etc.) whenever possible.
- If a document becomes critical, it is explicitly cited from a DISC, ADR,
  or SPEC with its relative path.

## Language

YAML keys, status enums, IDs, and template section headings stay in **English**
(the schema). All prose — descriptions, context, rationale, findings — goes in
the project's `content_language`, declared in
[`../../LANGUAGE`](../../LANGUAGE) (see §3.15).
