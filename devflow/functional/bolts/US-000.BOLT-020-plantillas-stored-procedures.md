## 1. Description

Se entrega el conjunto de plantillas de stored procedures: los scripts que el consumidor aplica contra su base, emitidos **uno por procedimiento**, con T-SQL propio del motor de base soportado y sin la separación de lotes frágil del set legacy.

---

## 2. Expected outcome and completion evidence

- **Objective:** que el consumidor obtenga los scripts de su base de datos generados desde el modelo, **sin** la fragilidad de empaquetado del set legacy y **sin** apoyarse en objetos de sistema obsoletos, de modo que el procedimiento de cada nodo del modelo sea un artefacto identificable por sí mismo.
- **Completion criterion:** el set cubre los procedimientos que el modelo declara y **cada uno se emite como un artefacto propio**, trazable al nodo del modelo que lo origina; la separación de lotes **no depende del contenido** del script (un literal que contenga el separador no lo rompe); el T-SQL emitido **no** se apoya en los objetos de sistema obsoletos que usaba el set legacy; el mapeo de tipos que las plantillas necesitan se **consume** del contrato del modelo y no se redefine en ninguna plantilla; el motor **emite** los scripts y **no** los aplica contra ninguna base; el contenido que el modelo declara como paso posterior a la generación se emite como artefacto, nunca se ejecuta; y el comportamiento es equivalente al de los scripts generados de 1.4, con las diferencias declaradas.
- **Expected evidence:** la emisión **uno por procedimiento** sobre el modelo de referencia, con el listado que traza cada artefacto a su nodo del modelo; la comparación contra los **scripts generados de 1.4** como referencia dorada, con cada diferencia declarada y atribuida (modernización del T-SQL, empaquetado, retiro de la dependencia de la plataforma web) — no queda margen para comparar contra el motor legacy en ejecución; el caso de un script cuyo contenido incluye el separador de lotes y que **no** se rompe; la constancia de que no se emiten referencias a los objetos de sistema obsoletos; la constancia de que el mapeo de tipos proviene del contrato del modelo y de que **no** existe una segunda tabla en el set; la evidencia de que el motor no abre conexión ni aplica ningún script (ADR-003 §3.1); la verificación de que lo emitido aplica **sin error** sobre una base limpia del motor soportado, y la constancia de que el procedimiento de post-generación declarado por el modelo se emite y no se ejecuta; la entrada propia de las rupturas que este Bolt introduce, registrada en las notas de migración en el mismo acto que el cambio (ADR-008 §3.1).
- **Scope:** las plantillas de stored procedures del set —los procedimientos que el modelo declara y los que acompañan a las relaciones entre entidades, incluida la función de descripción cuando el modelo la pide—; el empaquetado **un archivo por procedimiento** y la desaparición de la separación de lotes por contenido; el T-SQL que se emite, sin los objetos de sistema obsoletos; el consumo del mapeo de tipos del contrato del modelo (sin redefinirlo) y de los helpers de generación que ese mapeo usa para escribir tipos e identificadores; y la emisión del contenido que el modelo marca como paso posterior a la generación.
- **Exclusions:** no implementa el motor ni su contexto de render (Bolt 017) ni la herramienta de línea de comandos (Bolt 018); no entrega el set de clases C# (Bolt 019) ni las plantillas de proyectos y configuración (Bolt 021); **no aplica** ningún script contra una base ni implementa el pipeline que los aplica (ADR-003 §3.1: el motor emite, el consumidor aplica); no reescribe el esquema de la base del consumidor ni migra datos; no agrega motores de base alternativos (ADR-001 §3.5 / OQ-005: hay un solo motor soportado); no decide el mapeo de tipos —es el dato portable del contrato del modelo (ADR-001 §3.1)— ni lo duplica; no agrega capacidades al modelo que el formato no declara (la limitación conocida sobre vistas, ADR-002 §3.1, se declara y no se rellena).
- **Risks / controls:** *el consumidor aplica estos scripts contra su base* → el riesgo es el más alto de la familia: la emitibilidad por nodo, la comparación contra la referencia dorada y la verificación sobre una base limpia son parte de la aceptación, y el set **no** aplica nada por su cuenta; *modernizar el T-SQL y romper una comprobación de existencia* → lo que se emite se verifica sobre una base limpia y las diferencias con el dorado se declaran una por una; *separación de lotes que vuelva a depender del contenido* → hay un caso explícito con el separador dentro del contenido; *un script que se pierda por empaquetarlo mal* → un artefacto por procedimiento con su trazo al nodo del modelo, y la colección ordenada de forma canónica; *duplicación del mapeo de tipos* → el mapeo es el del contrato del modelo y el set no define una tabla propia; *ejecución accidental de SQL desde el motor* → el contrato de exclusión es explícito y se verifica por ausencia de conexión.

## 4. Dependencies

- **Governing sources:** US-000 (parent); REV-001 — F-46 (los objetos de sistema obsoletos en los checks de existencia y la separación de lotes por coincidencia de texto) y F-37, y §6 ítem 18; **ADR-003 §3.1** (un archivo por procedimiento, la desaparición de la separación de lotes por texto, el motor que **emite y nunca aplica** SQL, y el consumo del mapeo de tipos del contrato del modelo como fuente única) y **§3.5** (las plantillas como datos con su versión, los helpers que consumen el mapeo y la regla de que el mapeo no se redefine); ADR-001 §3.1 (el mapeo de tipos SQL↔CLR como dato portable único, consumido por el reverse y por el motor, y la frontera de lo que migra al tooling) y §3.5 (un solo motor de base soportado); ADR-002 §3.1 (el límite conocido del modelo y la regla de no inventar el dato que no existe).

- **External:** una base del motor soportado, limpia, donde el consumidor (o la lane de integración de este Bolt) aplique los scripts emitidos para verificar que aplican sin error.
